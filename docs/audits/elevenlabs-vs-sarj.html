ElevenLabs vs Sarj, and what the design system is missing

The Sarj product, the Sarj design system and ElevenLabs Agents, measured against each other. The point is the design system: the competitor and the product are measured so it can decide what to own next.

1 · The short version

Five findings carry most of the weight

1

The system covers generic SaaS, and almost none of the voice product

Surfaces, forms, tables, index-page states, motion and z-layers are written down. The recording player, transcript, turn timing and latency, live-call state, charts, value formatting and Arabic content are not. The product builds all of them by hand, the mockups do too, and both already disagree with themselves.

2

The system and the product are two different shadcn styles

The product is new-york on Base UI, and the system is radix-nova on Radix. Every shared control is one step taller in the product. The control-scale topic says 24/28/32/36 px; the product ships 24/32/36/40, so every mockup installed through the registry renders a step smaller than the product around it.

3

Status is painted five ways in the product, four in the mockups

The system has the tint tokens but no Badge variant that uses them, and its chip key covers four call statuses. The product's Badge falls back to raw green-50, amber-50 and red-50.

4

The docs contradict the code in six places

  • AGENTS.md and three skills say charts are "one purple ramp". Since DES-174, globals.css:79-108 has six separate hues.
  • data.ts:439 still sends drawer help text to an (i) tooltip, against the inline-description house rule.
5

ElevenLabs is ahead on three things Sarj has no pattern for

  • Versioning: draft, then a diff, then publish, with branches.
  • Per-turn latency in the transcript.
  • Evaluation criteria and extracted data, defined and inspected on one screen.

Sarj is ahead on quality flags pinned to the waveform, the Scenario Copilot, the Arabic end-of-utterance model, batch calling with retries, and the Salla and Zoho automations. None of those has a design-system pattern either.

Holes that are not voice-specific

  • Toasts. Nothing says when to use a toast rather than inline feedback, or covers copy, duration or undo. One mockup puts a secret in a toast (connected-apps/create-token-dialog.tsx:228).
  • Accessibility. The page has two rows. Missing: contrast per token pair, the 24px hit-target floor (17 icon-xs buttons), icon-button naming, heading levels, live regions for call status, and audio keyboard controls.
  • Content. Lives only in the sarj-no-slop skill; the written system has no Content section.
  • Arabic content. ui-review:15 waives RTL entirely. For an Arabic-first product, the waiver should cover UI mirroring only. There is nothing on dir="auto", bidi isolation, the Arabic fallback font (Nunito has no Arabic glyphs, inferred), or numerals.
  • Pagination. Written, but no mockup shows it and the primitive is unused.
6 · Recommendations

Design-system fixes, in order

Ranked by reach × how fast it drifts ÷ effort. Each is sized as one ticket.

1

Correct the documentation contradictions

Chart wording, help-text rule, scrollbars, shadows, radius, primitive count, token list.

Agents follow these skills today and build monochrome charts and (i) tooltips against the rules.

S
2

Decide the control scale

The system moves to a 36px default, or the product migrates to 32px. Record it in control-scale. Needs a design-lead decision.

Every registry install is off by one step until this is settled.

decision
3

Intent Badge and a Status topic

success / warning / info variants on the tint tokens. One status map (call, live call, batch, flag, source, token, connection, report) with icon rules and a live signal: a dot plus elapsed time, safe under reduced motion. Ship the tint tokens to the product.

Five paint systems in the product, four in mockups.

M
4

Formatting foundation and src/lib/format.ts

One date format with relative-time rules; m:ss / h:mm:ss; latency in ms under 1 s and one decimal above; counts; file size; phone with dir="ltr"; one empty-value glyph; tabular-nums on numeric columns.

~10 formatters in the product, 7 in mockups, two disagreeing on the same ticket.

M
5

Voice pattern group and shared blocks

RecordingPlayer (flag and alert markers, speed, keyboard, unavailable state), Transcript (speaker roles, tool rows, per-turn latency, search, seek, follow the playhead), CallHeader, a metadata key-value list. Promoted from the two mockup forks with one data model.

The core surface, the largest block of duplicated UI, and where ElevenLabs is visibly ahead.

L
6

Filter bar, time range, copy button, page header

Shared blocks and topics.

The top two repeated patterns in the product.

M
7

Review-diff pattern

Unsaved-changes bar, review dialog (added, removed, modified), optional note, concurrent-edit banner. Versioning stays a product call; the pattern is needed either way.

7 product files, 3 flows.

M
8

Arabic content page

dir="auto" for user content, one languageDir() (ar, ur → rtl), bidi isolation, fallback font and line height, numerals. Narrow the ui-review waiver to UI mirroring.

An Arabic-first product with no Arabic rule, and a live Urdu bug.

S
9

Charts and stat tiles

Which chart for volume, outcomes and latency distribution; axes on border and muted-foreground; empty and partial charts; tile anatomy.

Six chart tokens, no rules; the product's tiles use shadows.

M
10

Forms decision and the settings row

Document Form beside Field, or state that Field replaces it. Add the settings-row shape: label, description, control; slider plus number.

The system teaches a form layer the product never uses.

S
11

Pickers

Combobox for single and multi; time, timezone and date-range as primitives or documented compositions.

Six product-only primitives exist because the system has no answer.

M
12

Destructive actions and toasts

Confirm vs undo, dialog copy formula, toast types, no secrets in toasts.

Two rules already conflict.

13

Editors

Long-prompt editor, {{variable}} chip on a real token, code / JSON block, key-value editor.

Three editors and three variable parsers in the product.

7 · Reference

What to take from ElevenLabs

Structure and behaviour only, and only when a ticket calls for the surface. Never its visual style.

Take

Per-turn latency chips and inline tool rows in the transcript · evaluation criteria with pass/fail and a reason each · analysis definitions and results on one screen · a setting that changes one field sits on that field · system tools as one toggle list with per-tool config · review diff before publish, with live/draft in the header · a template gallery that previews structure · the uniform empty state: icon, title, reason, action.

Don't take

The monochrome style, type and radii · promo cards inside working screens · ten editor tabs mixing deployment with agent config · long filter-chip rows with no grouping · features the ticket did not ask for (tests, branches, traffic split, URL crawling).

The same reference, per surface, is the sarj-elevenlabs skill in this repo.

8 · Limits

What was not checked

  • The ElevenLabs app itself. Not walked in a signed-in browser yet. Not seen anywhere: in-editor voice settings (stability, speed), the Users page, parts of Advanced, Settings, Developers, WhatsApp. Mobbin captures date from Mar–Apr 2026 and may have changed.
  • No route was rendered in either repo, and no lint, typecheck or screenshot was run. UI claims come from source.
  • The product audit reads code; it does not know which admin screens real users see most.
  • Whether a single product screen mixes inline help with (i) tooltips was not checked screen by screen.
